# 実機テスト手順（iPhone / Expo Go）

この手順は Expo Go での前面表示・充電運用を確認するためのもの。本番配布やロック中の鳴動保証の合格判定とは分ける。**ここに書かれた挙動はすべて「実機で未確認」**であり、Simulator・自動テストの結果で代替しない。

## SDK について

- プロジェクトの SDK は Expo SDK 57 に固定済み（`AGENTS.md` の方針）。SDK メジャーは変更しない。`expo` / `expo-asset` / `expo-notifications` などの 57.0.x パッチ更新は、`expo install --check` と CI に合わせる定例作業として行う。
- 一方、**物理 iPhone の Expo Go が対応する SDK は未確認**。パッチ更新やマージはこの確認を待たないが、実機へ引き渡す前に必ず確認する。
- 開始前に、iPhone の Expo Go が対応する SDK、`package.json` の実依存、配信 manifest の SDK を照合して記録する。不一致なら開始しない。
- `expo doctor` / `expo export` / HTTP 200 は実機起動の証明ではない。

## 確認の区分

| 区分 | できること | できないこと |
| --- | --- | --- |
| 自動テスト（`npm test`） | 判定ロジック、保存・復旧の状態遷移 | 画面表示、通知配送、VoiceOver |
| `npm run typecheck` / iOS export | 型と bundle の成立 | 実行時の挙動 |
| Simulator | レイアウト、基本操作 | 歩数計、通知音、ロック中の鳴動、Focus/消音、触覚、実際の VoiceOver 読み上げ |
| 実機（Expo Go） | 上記すべて。ただし Expo Go 固有の制約あり | 配布ビルド固有の挙動（別途ビルドで確認） |

## 開始条件

- iPhone の機種、iOS、Expo Go のバージョンと対応 SDK を記録。
- 試験対象 commit、時刻、通知/モーション権限、消音/集中モード/音量、Watch 接続の有無を記録。
- 既存のアラームは削除しない。テスト用アラームを作り、終了後にそのアラームだけ削除する。
- keep-awake の確認は production JS（`expo start --no-dev --minify`）で行う。開発モードの常時点灯をアプリ機能の成功と誤認しない。

## 手順と期待結果

1. **追加**: 一覧→追加→時刻と繰返しを選ぶ。初回日時が意図どおりか確認。直前すぎる時刻（10 秒未満）は「時刻を選び直してください」と出て追加できない。2〜3 分後のテストアラームを追加し、歩かず待つ。指定時刻に鳴り、停止で今回分だけ終わり、繰返し設定が残る。
2. **鳴動中の一覧**: 鳴動中はオン/オフと削除が無効。削除の確認ダイアログを開いたまま鳴動が始まった場合も、「削除」を押しても実行されず説明が出る（最新状態で再判定）。停止ボタンを操作できる。
3. **60 分より先**: 計測開始時刻の予告だけが出る。歩いても進捗や自動停止に反映されない。
4. **10 分後**: アプリを表示して歩く。99 歩以下では予定が残り、100 歩到達後は該当回の日付と停止理由が出る。歩数計の更新は遅延/まとめ通知があり、足踏みの数と表示は一致しない場合がある。
5. **近接した 2 つ**: 1 つ停止した直後に 2 つ目が同じ歩数で停止しない。
6. **背面**: 途中まで歩き、別アプリへ切り替えて歩き、戻る。背面中の歩数は加算されない。
7. **モーション権限拒否**: 設定で拒否して戻る。「歩数の利用が許可されていません。歩数による停止を確認できません。予定を確認してください」（英語の端末では "Step access isn’t allowed." で始まる文）と、小さいコード `SENSOR_PERMISSION_DENIED` が状態行に出て、進捗バーが消える。予定を勝手に取り消さない。許可して戻ると計測が再開し、表示が復旧する。設定を元に戻す。
8. **通知オフ**: 警告カードと設定への導線が出る。戻して復帰すると再検査/補充される。既存予定を無条件に成功と表示しない。
9. **自動ロック**: 24 時間以内の予定がある状態で自動ロック時間を越えて待つ。画面が消えない。全テスト予定をオフにすると通常の自動ロックに戻る。
10. **ロック/別アプリ中の時刻**: 手動ロック・別アプリ表示の状態で時刻を迎える。前面ループ音とは別に通知配送/音を記録。消音/集中モードは別々に記録し、無音を成功としない。
11. **鳴動後ロック**: 前面で鳴り始めた後ロックし、音が続くか記録（設定上は継続するが**未確認**）。戻って停止できる。
12. **確認通知**: 本文タップだけでは停止しない。通知内「起きています」を期限前に押した場合の停止対象を記録。Watch/終了状態は別表とし、未対応を成功としない。
13. **再起動**: アプリを終了/再起動して予定が保持される。前面復帰で先の予定が補充され、予約期限が更新される。
14. **文字サイズと VoiceOver**: 最大文字サイズで、初回日時・警告・停止操作に到達できる。通知バナーの記号と「×」が欠けず、閉じるボタンが押しやすい。鳴動開始時、VoiceOver のフォーカスが停止ボタンへ移り（別の読み上げは行わない）、「◯◯:◯◯のアラームが鳴っています。アラームを止める」（英語・12 時間設定なら「The 7:00 AM alarm is ringing. Stop alarm」）と読まれる。追加画面を開いたまま鳴動が始まった場合も、画面が閉じた後に同じ読み上げになる。文字サイズを戻す。
15. **保存失敗カード**: 保存データを読めない状態は再現手段がなく**未確認**。表示されるなら、アプリの完全終了→開き直し→端末再起動の順の案内があり、その手順自体は初期化や削除を求めないこと。カード末尾の「通知を解除してリセット」は2回の確認の後だけ実行され、最大文字サイズ・小さい画面でもボタンと確認文に到達できること、Expo Go では他プロジェクトの予約通知が残ることも未確認（再現手段がなく、実機・Simulator では未実行）。
16. **設定とデータ削除（未確認）**: ヘッダーの「⋯」（VoiceOver: 設定とプライバシー）で sheet が開き、最大文字サイズでも要約と「データを削除」に届くこと。削除は2回の確認の後だけ実行され、成功後は一覧が空になり予約済みの通知が残らないこと（他アプリの通知は残る）。鳴動中は「⋯」が無効で、sheet を開いたまま鳴り始めたら閉じて停止ボタンが最優先で出ること。通知を解除できない状態の再現手段は実機にないため、失敗時の表示は自動テストのみ。

17. **OS キューとの照合（ALR-003/008、全項目未確認）**: ①設定アプリで通知をオフ→オンにして戻る（予約が消えるか、再予約されるか、行の警告が消えるか記録）。②iOS の設定から Expo Go の通知を消去できる場合は消した後に戻り、行が「確認できません/見つかりません」→再予約の notice になるか。③設定で日付と時刻の「自動設定」をオフにして手動で時刻を進める/戻した後にアプリへ戻る（iOS の予約は絶対 UTC の CALENDAR トリガーに変えたため、**この項目で正時に鳴るか・旧ビルドの予約が移行されるかが初めての確認**になる。自動テストでは証明できない）。④端末のタイムゾーンを別地域へ変更して戻る（繰り返しは新しい壁時計 HH:mm、今日だけは元の日付）。⑤端末を再起動して戻る。各項目で、2〜3 分後のテストアラームを使い、実際に指定時刻に鳴ったか（再予約が OS に届いたか）を必ず確認する。通知センターに届いている無関係なアプリの通知が、この操作で消えたり変わったりしないことも見る（iOS には、このアプリの保留中の通知を一覧で確認する画面は無い。確認は「実際に鳴ったか」だけで行い、一覧の確認を前提にしない）。⑥通知が 64 件に近い状態（Expo Go の他プロジェクトを含む）でタイムゾーン変更後に戻り、「上限(64件)」の警告が出て古い予約が残ること、64 件超過時に OS がどれを捨てるか（未検証）を記録する。⑦iOS では保留通知の発火時刻が SDK から読めないため、時刻のずれは内容照合では検知できない。

18. **診断コード付きの案内（未確認）**: 自動テストで失敗経路とコードの対応は確認済みだが、実機の表示は未確認。確認できる範囲: (a) 設定アプリで通知をオフにして追加すると「通知が許可されていないため、アラームを予約していません」と小さいコード `NTF_PERMISSION_DENIED` が出て、一覧にアラームが増えない。(b) 歩数の許可を拒否すると状態行に `SENSOR_PERMISSION_DENIED` が出て、設定を開くボタンがある。(c) 最大文字サイズで通知バナーの本文・コード・「×」が欠けず、コードが本文を押しのけない。保存破損・取り消し不明・起床確認だけの失敗は実機で再現できないため自動テストのみ（未確認）。予約通知を一覧で確認できなかった場合（MAIN_UNVERIFIED）は、その通知IDを記録して新しい予約を止め（MAIN_RECONCILE_PENDING）、アプリを開き直すと確認して整理する設計だが、実機では再現できず未確認。編集の失敗（`EDIT_*`）と、予約を確認できずアプリが記録も取り消しもできなかった場合（`MAIN_UNVERIFIED_MEMORY_ONLY`）も実機では再現できず自動テストのみ。iOS ではアプリが自分の予約済み通知の一覧を端末上で見る手段がないため、どの案内も「通知一覧を確認」とは書かず、アプリの開き直し・設定の「データを削除」（アラーム設定も消える）・別の目覚ましの併用だけを案内する。物理端末の受け入れは完了としない。

## Android の通知 channel 警告 — 実機未確認

自動テストは判定ロジックのみ。実機での結果が出るまで「実機確認済み」と扱わない。

1. **Android 8 以上（API 26+）**: 端末設定でアプリのメインのアラーム channel を「重要度: 低/なし」または「音なし」にして戻ると、警告が出る。元に戻して前面復帰すると警告が消える。アプリ全体の通知オフでは従来どおりの警告が出る。
2. **Android 7.x（API 24/25、実機/Emulator があれば）**: channel が無いため、通知を許可した状態では警告が出ず、通知をオフにすると従来の警告が出る。API を確認できない端末では警告側に倒れる（誤って安全と表示しない）。
3. 起動直後（channel 作成前）に警告が一瞬出ないかを記録する。
4. iOS は変更なし（権限のみ）。

## 停止（100 歩/起床確認）の保存復旧 — 未確認

通知の取り消しには成功したが状態の保存に失敗した場合の復旧は、自動テストでのみ検証している。実機では失敗を意図的に起こせないため**未確認**。次の挙動が設計上の期待:

- 保存に 2 回失敗すると「停止の記録を保存できません」の警告が残り、「アラームは有効」とは表示しない。アプリを開き直す/前面復帰で復旧を再試行する。
- 取り消し結果が不明（例外・中断）の場合は「停止・予約の状態が未確認です」の警告が残る。OS に予約が残っていれば未実行として解消、予約が無い場合は鳴る/鳴らないを断定せず警告を維持する。
- 復旧は記録された正確な ID のみを対象にし、無関係な通知は取り消さない。
- 停止処理と復旧の排他は同一プロセス内のみ。記録が `cancelling` のまま OS 予約も無い場合は、取り消し済みか発火済みか区別できず「未確認」のままになる（実機では再現できない）。

## 既知の制約（本番要件/仕様判断として分離）

- アプリ非表示時の歩数は数えない。
- 数日アプリを開かない場合の継続補充は保証しない。
- 終了状態の Watch 応答は未対応・未確認。アプリを開けなかった／30 分以上放置した未停止回は鳴らず、「見逃したアラーム」に出る（音なし、起きたかは判断しない。実機で未確認。項目 20 の③）。30 分以内に発見した回だけが鳴動に戻る。
- 音声読み上げ（VoiceOver）のフォーカス移動のタイミング（300ms/700ms、iOS の追加画面は onDismiss 後 100ms の待ち）は**未測定**。通知バナーの読み上げと競合する可能性がある。

## アラームの編集 — 未確認

一覧の「編集」の実機確認は未実施。次を確認して結果を返す（自動テストはロジックのみ）。

1. **事前入力**: 「編集」で追加フォームが現在の時刻・繰り返しで開き、タイトルが「アラームを編集」、確定が「この内容で保存」になる。最大文字サイズ・iPhone SE 相当の小画面でも、編集ボタンと全操作へ到達できる。VoiceOver で「◯時◯分、…のアラームを編集」と読まれる。

3. **鳴動中**: 鳴動中は「編集」が無効で、編集画面を開いたまま鳴動が始まった場合は画面が閉じて保存されない。
